# 现场演示脚本 + 追问预案

目标：8 分钟内讲完"是什么 / 为什么这么做 / 技术亮点在哪"，并让面试官自己动手点两下。

---

## 0. 演示前 3 分钟自检

```bash
npm run demo:check     # 10 秒：JD 能拆、9/10 份简历能解析（07 是扫描件，失败是预期）
npm start              # 打开 http://localhost:5178
```

- 确认右上角模式徽标是预期的那个：想演示降级就说"**规则模式**"，想演示真模型就确认是「LLM 模式」。
- 确认页面是空的（点右上角「重新开始」清一下上一轮）。
- 心里记住一个数：**10 份简历、3 秒内跑完**——这是最容易被记住的对比。

如果现场没网 / Key 失效：直接说"正好，我把 Key 摘了，你看它自己降级到规则引擎，全流程照跑"。**这不是救场话术，这就是设计目标之一。**

---

## 1. 开场（30 秒，别念功能列表）

> 这个 Demo 解决一件很小但很烦的事：HR 一天收到几十份实习简历，一份看两分钟，看完还得写"为什么不要他"。
>
> 市面上很多 AI 简历工具的做法是让模型"打个分"。我没这么干，因为模型给的分既不稳定也说不清。我的做法是——**模型只负责判断每一条要求符不符合，并指出简历里哪句话支持这个判断；分数由代码算。**
>
> 所以同一份简历跑两次，结果一模一样；每一个数字点开都有依据。

（这句话是全场的核心论点，后面所有技术细节都是它的展开。）

---

## 2. 痛点（1 分钟）

> 三个具体的痛点：
>
> 第一，重复劳动。同一份 JD，第 30 份简历和第 1 份要看一样多的字。
>
> 第二，标准不一致。上午和下午的标准都不一样，换个人更不一样。
>
> 第三，说不清。淘汰一个人，得能说清是哪条不满足，不能是"感觉不太合适"。
>
> 所以这个工具要做的不是"替你决定"，是**替你看完，并把依据摊开**。最后点"联系"的永远是人。

---

## 3. 主流程演示（3 分钟，四步）

### 第 1 步：JD → 评分表（45 秒）

操作：点「填入示例 JD」→ 点「① 拆解成评估项」。

> 我用的是一份真实的岗位 JD——BOSS 直聘上一家 B2B 外贸公司的「AI 自动化项目实习生」。
>
> 点一下，它把这段自由文本拆成了 9 条**可判定**的要求：3 条硬性、6 条加分。每条带类型、权重、还有一句"要问什么"。
>
> 注意两点：
> 第一，**权重是 HR 可以改的**。这个岗位如果更看重编程，把编程从 8 调到 10，所有人的分数立刻重算——标准是显式的，不是藏在模型脑子里。
> 第二，像"有主动学习能力""愿意理解业务逻辑"这种**软性要求被主动剔除了**，因为它没法从简历里判定，留着只会让模型瞎猜。宁可少判一条，不要判一条假的。

### 第 2 步：10 份简历一起跑（40 秒）

操作：点「用内置样例简历跑一遍」。

> 这 10 份不是随便写的，是我照着"人工初筛最容易看走眼的情况"造的：专业不符但自学很强的、经历不错但没写时长的、全英文的、只有三行的、还有一个是扫描件。
>
> 3 秒，10 份跑完，按匹配度排序，并且已经分好组：建议复核 2 位、待定 5 位、暂缓 1 位、信息不足 1 位、1 份读不出来。

### 第 3 步：点开第一位（60 秒，这是全场重点）

操作：点「张思远」。

> 匹配度 90%，但比分数更重要的是下面这些。
>
> **每一条判定都挂着简历原文。** 比如"计算机相关专业"这条，依据是"2023.09-2027.06 华中科技大学 计算机科学与技术 本科"，这是从 PDF 里抽出来的原句，不是我编的。
>
> 而且这句原文会被**拿回去做包含性校验**——模型说的每一句引用，都要能在简历里找到；找不到就标成"未核验"，界面上是琥珀色。这是防模型编造依据的最后一道闸。
>
> 往下滚：追问清单。简历里没写清楚的，它会直接生成一句可以发给候选人的话。

### 第 4 步：点开"信息不足"的那一份（45 秒，全场最容易被记住的一下）

操作：点「赵一鸣」（32 分）。

> 这份简历只有三行，大部分人看到会直接判"不合适"。
>
> 但你看它的结论——不是"暂缓"，是**「信息不足 · 需补充简历」**，信息覆盖率 41%，6 项"待确认"。
>
> 因为我给判定分了四态：符合、部分符合、不符合、**待确认**。**简历没写 ≠ 他不具备。** 没写可实习时长，可能只是没提；判成"不符合"就是误杀，判成"符合"就是放水。
>
> 所以第四态单独一档：不计分，但扣覆盖率；覆盖率低于一半，工具就不下结论，而是告诉你"这份得再问一句"。这就是我理解的"AI 辅助"和"AI 替你做决定"的区别。

## 4. 技术亮点（2 分钟，按面试官兴趣挑两三个讲）

**① 为什么分数一定要由代码算**

> 我试过让模型直接给匹配度，同一份简历两次跑出 78 和 91。改成"模型逐条判四态 + 代码加权"之后，结果是确定的，而且可以写单元测试——现在有 22 个测试，打分公式、结论短路顺序、证据校验、解析、HTTP 端到端，连模型调用链路都用假上游测过了。
>
> 附带好处：模型偶发判错一条，只影响那一条的权重，不会污染总分。

**② 结论不是拍阈值，是短路规则**

> 结论按顺序短路：红线 → 两项以上硬性不满足 → 覆盖率太低 → 单项不满足 → 才对"全部满足"的给建议复核。
>
> 特别注意最后一条：**只有硬性要求一条不缺，才配拿"建议进入人工复核"。** 一个人 78 分但有一项硬性没写清楚，结论只能是"待定"。宁可多问一句，不要放过一个错的人——招聘的代价是不对称的。

**③ 双引擎：规则和模型同一套 schema**

> 我这个 Demo 有两种模式。有 Key 走大模型；没 Key 走一个我写的规则引擎——学历专业匹配、技能词命中（命中一个词只给"部分符合"，两个以上才算"符合"）、否定语境识别（"本人无编程基础"不能算命中"编程"）、实习时长解析。
>
> 它不只是兜底：**它同时是模型判定的对照组**。演示的时候可以直接切换，看两种模式对同一份简历的判断差异。

**④ 工程上的取舍**

> 前端是原生 HTML + CSS + JS，没有构建步骤。理由很俗：现场演示第一优先级是"一定能跑"，少一层打包少一类故障。
>
> 进度用 900ms 轮询而不是 WebSocket——3 秒跑完的批次，不值得引入长连接和断线重连。
>
> 单进程、单端口、数据落 JSON 文件；`store.js` 是唯一持久化出口，将来换数据库只改这一个文件。

---

## 5. 收尾（30 秒）

> 一句话总结这个 Demo 的设计取向：**它不替 HR 做决定，它替 HR 做"看简历"这件体力活，并把判断依据摊开。**
>
> 我能立刻说出的局限也在这儿：工作年限的复合表述还会判不准；扫描件我不做 OCR，因为 OCR 质量不稳会污染判定，宁可提示 HR 换一份文本版。这些都在 README 的「已知限制」里写了。

## 6. 追问预案

### 产品 / 业务

**Q：HR 真的会信一个 AI 的分数吗？**
得分不是目的，排序和依据才是。所以界面第一屏给的是"谁值得先看"，而不是"谁被淘汰"。我还刻意让结论里出现"待定 · 建议补充信息"这种不完全结论——工具承认自己不确定，HR 才敢用。

**Q：为什么不直接让模型写一段候选人评价？**
写了，在详情页最上面那句 headline，还有优势/风险两栏。但那是**锦上添花**，排在逐条判定之后。评价性文字不可核对，判定+证据可以核对，所以顺序不能反。

**Q：这个给谁用？**
第一版是给"一天要看几十份简历、没有 ATS 系统"的中小企业 HR。大公司有 ATS，我的切入点反而应该是"把 ATS 里的简历批量过一遍"。

**Q：会不会有算法歧视的问题？**
这正是我把"软性要求"剔除的原因——年龄、性别、婚育、籍贯这类信息不参与判定；评分表只保留与岗位能力相关的条目，而且这张表是 HR 自己确认过、可编辑、可审计的。输出永远只是"建议"，不做自动淘汰。

### 技术 / AI

**Q：怎么保证模型不瞎编？**
三道闸：① 判定必须是四态之一，schema 强约束；② 每条判定必须给简历原文片段，代码做包含性校验，找不到就标"未核验"；③ 提示词里明确写"宁可 unknown 不要 met"。

**Q：模型返回的 JSON 解析失败怎么办？**
`provider.js` 里做了三层：去掉 ```json 围栏、截取首个 `{` 到末个 `}`、修尾逗号；如果服务端不支持 JSON 模式（400/422）会自动去掉 `response_format` 重试一次；还是失败就这份简历降级到规则引擎，批次不中断。

**Q：成本怎么算？**
每份简历 1 次调用（我把"抽字段"和"逐条判定"合并成一次，省一半 token），10 份简历大约几千 token。真要上量，第一件事是把 JD 的 rubric 结果缓存起来按岗位复用。

**Q：怎么评估准确率？**
现在还没有标注集，这是最大的短板。下一步我会先用 30-50 份真实简历做人工标注，测两个指标：判定一致率（模型四态 vs 人工四态）、以及"最终结论翻转率"——后者更重要，因为 HR 只看结论。

**Q：为什么不用 RAG / 向量检索？**
这活儿里没有"检索"的需求。JD 只有一段、简历只有一份，全部塞进上下文就够了，向量库只会增加一层不可解释的中间环节。

**Q：规则引擎是不是在重复造轮子？**
规则引擎的目的不是替代模型，是**可对照的基线**。没有它，我无法回答"模型到底比规则强在哪"；有了它，答辩的时候可以说"这一条模型判对了、规则判错了，因为规则不懂'自学做出来了类似的东西'"。

### 工程

**Q：为什么不拆前后端 / 不用 React？**
单进程单端口，`npm install && npm start` 就能跑。现场演示的可靠性权重远高于工程优雅。真要长成一个产品，第一步是把 `pipeline/` 抽成一个独立服务——它现在已经是纯函数 + 明确入参，抽出去很便宜。

**Q：并发怎么控制的？**
自己写的 `mapLimit`，默认 3。串行太慢，全并发容易撞模型限流。每份简历独立 try/catch，一份失败不影响其他。

**Q：数据存哪？会不会泄露简历？**
内存 Map + 防抖落盘到本地 `data/runs.json`，不出机器。配置真模型时才会把简历正文发往所配置的服务——这一点我在 README 里明说了，不做含糊表述。

**Q：测试怎么做的？**
`node:test`，22 个：打分公式（partial 0.6 折算、unknown 扣覆盖率）、结论短路顺序、证据校验（逐字/改标点/编造三种）、否定语境、中文专业匹配不被"数据统计"误伤、PDF/扫描件/文本解析、以及 HTTP 端到端（拆 JD → 跑 10 份 → 校验判定与 CSV）。

模型那条链路也没放过：本机没有 Key，我起了个假的 OpenAI 兼容服务，验证请求形状（JSON 模式、Bearer、模型名）、模型把 JSON 包进代码围栏时的容错、模型判定是否被真正采用、**模型编造的原文证据会不会被回验标出来**，以及模型 5xx 时是不是真的降级而不是整批挂掉。不然"有 Key 走真模型"这句话就只是嘴上说说。

**Q：没有 Key，你怎么知道真模型能跑通？**
诚实说：真模型的输出质量我没法在本机验证，这需要 Key 和费用。但**链路**是测过的——假上游证明了请求格式、解析容错、判定采用、证据回验、降级五件事都对；剩下的是 prompt 调优，那要靠真实数据迭代。所以我在 README 里把"规则模式实测"和"LLM 模式未在真模型上跑过"分开写，没有混为一谈。

**Q：如果给两周继续做？**
① 人工复核结论回写，统计人机一致率；② 同岗位历史批次对比，看标准漂移；③ 评分表模板复用（一次拆解，多岗位套用）；④ OCR 只做"识别失败就走人工"的兜底，不做全自动。优先级按"能不能提高 HR 的采信度"排。

### 关于自己

**Q：这个 Demo 里最有技术含量的部分是什么？**
不是调模型，是 `unknown` 这一档和它的连锁设计：判定四态 → 覆盖率 → 结论里多出一个"信息不足"分支 → 追问清单自动生成。它把一个"模型打分"问题，变成了"如何表达不确定性"的问题，而这个问题的答案决定了工具能不能被真正信任。

**Q：有什么没做好的？**
① 没有标注集，准确率是"看起来合理"而不是"测出来的"；② 双栏排版 PDF 可能串行；③ 复合时长表述（每周 3 天共 6 个月）只判部分符合。三条都在 README 的已知限制里，我没有藏着。
